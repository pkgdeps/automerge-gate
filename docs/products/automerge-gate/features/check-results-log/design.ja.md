# チェック結果のログの設計

[English](design.md)

## このドキュメントについて

この文書は、ゲートが[チェック結果のログ](requirements.ja.md)で定めた出力をどう作るか、そしてログが「ポーリングごとに1グループ、最後に平らな一覧」という形になっている理由を説明します。
親の Product は [automerge-gate](../../product.ja.md) です。

### 対象読者

ゲートが出力する内容を変更する人とエージェント。

### 前提知識

GitHub Actions のログのグループと、ステップサマリー。ログのグループは入れ子にできない。

### このドキュメントで扱わないこと

ポーリングのループと、チェックの読み方は、[チェックの集約](../check-aggregation/requirements.ja.md)で扱う。

## 実装方針

整形と出力を分けている。
純粋な関数だけのモジュールが、評価するチェックの一覧を文字列に変える。ポーリングの題、ポーリングの本文の行、そしてログの行とサマリー用の Markdown からなる最終結果である。
2つの実行処理がそれらの関数を呼び、書き出しを行う。これにより、private mode と public mode で同じ文面が出て、整形はジョブのログなしでテストできる。

### チェックを整形の関数に渡す方法

ポーリングのループは、各ポーリングの番号、状態、件数を知らせるが、チェックそのものは渡さない。
そのため、それぞれの実行処理の取得の関数は、最新のポーリングで評価したチェックを、実行処理が読める変数に覚えておく。
ループは、先に取得の関数を呼び、次にポーリングごとのコールバックを呼ぶ。コールバックがグループを整形する時点で、覚えている一覧は、そのポーリングが評価したものになっている。
ループのあとは、同じ変数が最後のポーリングのチェックを持っており、最終結果とステップサマリーに使う。

ループのコールバックを広げてチェックを渡すことも選べた。
実行処理の側で覚えておく方法を選んだのは、ループのインターフェースを変えずに済むためである。

コールバックは、ツールキットのグループ用の補助関数でグループを書く。この関数は、本文の処理が例外を投げてもグループを閉じる。ループはコールバックを待つので、グループが入り混じることはない。

### ポーリングごとに1グループにした理由

ログには3つの役割がある。誰かが見ている間、ゲートが動いていることを示すこと。ジョブがタイムアウトしたときに、何が未完了だったかの証拠を残すこと。チェックごとの最終的な判定を示すこと。
ポーリングごとのグループは、最初の2つに役立つ。
グループが開いている間は、その行が流れて見え、閉じると題だけに折りたたまれる。見ている人には、間隔ごとに題の付いた新しい行が見え、終わったあとのログはポーリングごとに1行になる。
題の経過時間は、時間が進んでいることを見えるようにするためのものである。

グループは入れ子にできないため、ポーリング全体や結果を包むグループは置かない。
private mode の「Setup」グループはこれと両立する。起動時の決まった情報を収めており、ポーリングが始まる前に終わるためである。

最後のポーリングのグループは、最終結果と同じ内容を繰り返す。
それは、そのポーリングの記録として残す。最終結果は、何も開かなくても見えるように、どのグループにも入れずに書く。

### 最終結果とステップサマリー

最終結果は、チェックを読み方で分け、それぞれを名前順に並べ、不合格を先に置く。読む人が探しているのは不合格だからである。
同じ分け方から、ステップサマリー用の Markdown も作り、件数の表のあとに足す。
表と Markdown の間には空行を書く。空行がないと、GitHub は表に続く見出しを生の文字として表示する。

未完了のチェックは数え、実行処理が警告として報告する。
ループは未完了のチェックがないときにしか終わらないため、未完了のチェックは起こりえない。この件数は、将来ループが変わったときのための備えである。

サマリーは、private mode の実行処理では補助関数が、public mode の実行処理ではその場の処理が書く。
Requirements の未決事項に記録したとおり、この2つはモードの行の名前が異なる。

## アーキテクチャ・シーケンス図

図は不要である。流れは次のとおり。ループがポーリングを終えると、実行処理が、覚えているチェックをグループに整形する。ループのあと、実行処理が、最後のチェックを最終結果とサマリーに整形する。

## データモデル・ER 図

この機能自身のデータはない。整形の関数の結果は3つの部分からなる。ログの行、サマリー用の Markdown（一覧するものがなければ空）、未完了のチェックの数である。

## API・インターフェース

### ジョブのログ

- ポーリングのグループ: 題は `[mm:ss] Poll #N — STATE, COMPLETED/TOTAL completed`。本文の行は `  <アイコン> <名前> (<ラベル>)`。
- 最終結果: `❌ Failed (N):` と `✅ Passed (M):`。行は `  - <名前> (<ラベル>)`。

### ステップサマリー

Requirements に書いた、見出し、表、「Check results」の Markdown。

## 外部サービスとの連携方式

なし。出力は、GitHub Actions のツールキットを通して、ジョブのログとステップサマリーのファイルに書く。

## データの取り扱い設計

チェックの名前、status、conclusion を、読んだままログとサマリーに写す。ほかには何も保存しない。

## 認証認可に関する特記事項

なし。ジョブのログとステップサマリーを書くのに権限は要らない。

## セキュリティ上の留意事項

Requirements に書いたこと以外は、なし。サマリーでは、チェックの名前をコードの書式で囲む。名前に含まれる Markdown は表示に反映されない。

## デプロイに関する特記事項

なし。

## 検討した代替手段

### 各ポーリングで未完了のチェックだけを表示する

本文を短くするなら、まだ未完了のものだけを並べる方法がある。本文は、すべてのチェックをその状態とともに名前順で並べる。2つのポーリングを行ごとに見比べられるようにするためである。短い形と比べた記録は残っていない。

### すべてのポーリングを1つのグループで包む

グループは入れ子にできないため、すべてのポーリングを包むグループを置くと、ポーリングごとのグループを作れない。

### 失敗の詳細をログに表示する

アノテーションとエラーメッセージは写さない。各チェックの GitHub のページで確認できる。

## 未決事項

[Requirements](requirements.ja.md#未決事項) にあるもの以外は、なし。
