# チェック結果のログ

[English](requirements.md)

## このドキュメントについて

チェック結果のログは、ゲートがポーリングしている間と終わったあとに、評価する各チェックの状態を名前付きで、ジョブのログとステップサマリーに表示します。
メンテナは、チェックを1つずつ開かなくても、どのチェックがまだ動いているか、どのチェックが失敗したかを確認できます。
親の Product は [automerge-gate](../../product.ja.md) です。

### スコープ

- ポーリングごとに書くログ。
- ジョブのログに出す、不合格と合格のチェックの最終的な一覧。
- ステップサマリー。

### スコープ外

- どのチェックを評価し、それぞれを合格、不合格、未完了のどれとして読むか。[チェックの集約](../check-aggregation/requirements.ja.md)を参照。
- アノテーションやエラーメッセージなど、失敗の詳細。そのチェックの GitHub のページで確認する。
- private mode のスキップ時の、チェックごとの出力。スキップではチェックを読まない。[ゲートモード](../gate-modes/requirements.ja.md)を参照。

## ユーザーストーリー

### ゲートが何を待っているかを見る

ゲートのジョブを見ているメンテナとして、ポーリングごとにすべてのチェックとその状態を一覧してほしい。ゲートが動いていることと、何を待っているかを、タイムアウトのあとでも確認できるようにするためである。

**受け入れ条件:**

Scenario: ポーリングが終わった場合、評価するすべてのチェックを並べた折りたたみ可能なグループがログに出る

- Given: ゲートは開始から5秒後にポーリングしており、評価する3つのチェックのうち `build` は失敗、`lint` は成功、`test` は実行中である。
- When: 最初のポーリングが終わる。
- Then: ジョブのログに、`[00:05] Poll #1 — pending, 2/3 completed` という題のグループがあり、その中に `❌ build (failure)`、`✅ lint (success)`、`🟡 test (in_progress)` の行がこの順に並ぶ。

Scenario: ポーリング中にジョブがタイムアウトした場合、それまでのポーリングはログに残る

- Given: ゲートは3回ポーリングしており、チェックの1つがまだ queued である。
- When: ジョブがタイムアウトに達する。
- Then: ジョブのログに3つのポーリングのグループがあり、最後のグループに queued のチェックが名前付きで出ている。

Scenario: 置き換えられた実行の結果を無視した場合、ログに一度だけそのことが出る

- Given: `slow` という名前のキャンセルされた check run が、より新しい実行に置き換えられたワークフロー実行に属している。
- When: ゲートが何度かポーリングする。
- Then: ジョブのログに、`ignoring slow (cancelled): a newer run of the same workflow replaced it` という行が、ポーリングごとではなく1回だけ出る。

### 結果を1か所で見る

プルリクエストがブロックされたメンテナとして、最後に不合格のチェックを名前付きで一覧してほしい。原因を探して、プルリクエストのチェックを見て回らずに済ませるためである。

**受け入れ条件:**

Scenario: 不合格のチェックがある状態でポーリングが終わった場合、ログは不合格を合格より先に並べる

- Given: ポーリングが、`build` は失敗、`lint` はキャンセル、`test` と `codeql` は合格、という状態で終わった。
- When: ゲートが最終結果を書く。
- Then: ジョブのログに、どのグループにも入らない形で、`❌ Failed (2):` に続いて `- build (failure)` と `- lint (cancelled)`、そのあと `✅ Passed (2):` に続いて `- codeql (success)` と `- test (success)` が出る。

Scenario: 不合格のチェックがない場合、Failed の部分は省かれる

- Given: ポーリングが、評価するすべてのチェックが合格した状態で終わった。
- When: ゲートが最終結果を書く。
- Then: ジョブのログには `✅ Passed (N):` の部分だけが出る。

Scenario: 評価したチェックがない場合、一覧は書かれない

- Given: ポーリングが、評価するチェックが0件の状態で終わった。
- When: ゲートが最終結果を書く。
- Then: ジョブのログには Failed の部分も Passed の部分もなく、ステップサマリーには「Check results」の節がない。

Scenario: ポーリングが終わった場合、ステップサマリーに件数とすべてのチェックが出る

- Given: ポーリングが、不合格1件と合格3件で終わった。
- When: ゲートがステップサマリーを書く。
- Then: ステップサマリーには、state を含む見出し、件数の表、そして不合格のチェックを `❌ Failed (1)` の下に、合格のチェックを `✅ Passed (3)` の下に並べた「Check results」の節がある。

Scenario: private mode でゲートがスキップした場合、ステップサマリーはチェックなしでスキップを示す

- Given: ゲートは private mode で、マージの意思がない push に対して動いている。
- When: ゲートがスキップする。
- Then: ステップサマリーには、`🟡 automerge-gate: skipped` という見出しと、`gate-mode` の行が `private` で件数が0の表があり、「Check results」の節はない。

## 機能要件

### ポーリングのグループ

**概要:** チェックを読めたポーリングのたびに、ゲートはジョブのログに折りたたみ可能なグループを1つ書く。

**入力:** そのポーリングで評価するチェック、ポーリングの番号、状態、ポーリング開始からの時間。

**出力:** 題が `[mm:ss] Poll #N — STATE, COMPLETED/TOTAL completed` で、本文に評価するチェックごとの1行を持つグループ。

#### 適用する条件

##### 題

`mm:ss` は、ポーリング開始からの時間を、0で埋めた分と秒で表す。分は59を超えても増え続ける。
`STATE` は `pending`、`success`、`failure` のいずれかである。
`COMPLETED` と `TOTAL` は、評価するチェックを数える。

##### 本文

各行は `<アイコン> <名前> (<ラベル>)` で、空白2つで字下げする。
アイコンは、合格のチェックが `✅`、不合格のチェックが `❌`、未完了のチェックが `🟡` である。
ラベルは、チェックに conclusion があればその値、なければ status である。
行はチェックの名前で並べ替える。ポーリングが変わっても順序は同じになる。

##### 対象のポーリング

最後のポーリングも含めて、すべてのポーリングにグループを書く。GitHub からの読み取りに失敗したポーリングには、警告の行だけが出て、グループは出ない。

### 最終結果

**概要:** ポーリングが終わったあと、判定を報告する前に、ゲートは最後のポーリングで評価したチェックを、読み方ごとに一覧する。

**入力:** 最後のポーリングで評価したチェック。

**出力:** どのグループにも入らない形で、`❌ Failed (N):` の部分と、続いて `✅ Passed (M):` の部分。それぞれ、チェックごとに `  - <名前> (<ラベル>)` の1行を、名前順に並べる。

#### 適用する条件

##### 空の部分

チェックが1つもない部分は省く。

#### 例外ケースでの振る舞い

##### 結果の時点で未完了のチェックがある

結果を書く時点でまだ未完了のチェックは、どちらの部分にも入れず、ゲートは `pending check(s) at result time: N` という警告をログに出す。
ポーリングは未完了のチェックがなくなったときにだけ終わるため、これは起こらない想定である。

### ステップサマリー

**概要:** ゲートは、実行の要約をジョブのステップサマリーに書く。

**入力:** state、件数、ポーリングの回数、最後のポーリングで評価したチェック。

**出力:**

- 見出し `<絵文字> automerge-gate: <state>`。絵文字は、`success` が `✅`、`failure` が `❌`、それ以外が `🟡`。
- 次の行を持つ表: `gate-mode`、state、除外前のチェックの総数、評価したチェックの数、完了したチェックの数、ポーリングの回数。
- `❌ Failed (N)` と `✅ Passed (M)` の一覧を持つ「Check results」の節。各行は `` `名前` — ラベル ``。空の一覧は省き、両方が空なら節ごと省く。

#### 適用する条件

##### モードの行

`gate-mode` の行の値は `private` または `public` である。private mode がポーリングしたかスキップしたかは、state の行で読む。

### そのほかのログの行

**概要:** ゲートは、ポーリングの前後に決まった行をいくつか書く。

**出力:**

- private mode では、イベント、プルリクエストの番号と先頭コミット、レビューの確認、判断とその理由を収めた、折りたたみ可能な「Setup」グループ。
- 置き換えられた実行の結果を無視するたびに1行。最初に無視したときにだけ書く。
- GitHub からの読み取りに失敗したポーリングごとに警告。

## データ要件

### 必要なデータ

- **評価するチェック:** ポーリングごとの、評価する各チェックの名前、status、conclusion。ジョブのログとステップサマリーに表示する。これらは GitHub がワークフロー実行とともに保持する。

### データ間の関係

チェックが1回のポーリングに属すること以外には、なし。

### 個人情報

この機能の出力には、なし。private mode の「Setup」グループに出るレビュアーの名前は、[ゲートモード](../gate-modes/requirements.ja.md)に書いている。

## 依存する外部サービス

なし。出力には、ゲートがすでに動いているワークフロー実行の、ジョブのログとステップサマリーを使う。

## セキュリティ上の留意事項

チェックの名前は、ワークフローと GitHub App が付けたものであり、そのまま表示する。リポジトリのワークフロー実行を読める人は、プルリクエストのチェックと同じように、これらを読める。
