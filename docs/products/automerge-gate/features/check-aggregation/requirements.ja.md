# チェックの集約

[English](requirements.md)

## このドキュメントについて

チェックの集約は、プルリクエストの先頭コミットの check run を集め、`success` か `failure` の1つの集約した判定になるまでポーリングします。
親の Product は [automerge-gate](../../product.ja.md) です。

### スコープ

- 先頭コミットのどの結果を評価するか。
- 1つの check run を、合格、不合格、未完了のどれとして読むか。
- check run を集約した判定へどうまとめるか。
- ポーリングの間隔、終わる条件、上限。
- ゲート自身のワークフローを評価から外すこと。
- アクションの出力。

### スコープ外

- ポーリングをいつ始め、判定をどう報告するか。[ゲートモード](../gate-modes/requirements.ja.md)を参照。
- ジョブのログとステップサマリーに表示する内容。[チェック結果のログ](../check-results-log/requirements.ja.md)を参照。
- `ignore-checks` の一致の決まり。その機能の Requirements はまだ書かれていない。この文書は、ルールがどこで適用されるかだけを述べる。
- 置き換えられた実行のどの結果を無視するか。「より新しい実行に置き換えられたキャンセル済みの実行」の Requirements はまだ書かれていない。この文書は、その処理がどこで適用されるかだけを述べる。
- ほかのツールが書いた、以前からある commit status。評価しない。

## ユーザーストーリー

### 先頭コミットのすべてのチェックを待つ

メンテナとして、どのワークフローや GitHub App が報告したものであっても、プルリクエストのすべてのチェックをゲートに待ってほしい。チェックを名前で並べずに済ませるためである。

**受け入れ条件:**

Scenario: 評価するチェックがすべて終わって合格している場合、判定は success になる

- Given: 先頭コミットに、2つのワークフローファイルと1つの GitHub App からの check run があり、すべて `success`、`skipped`、`neutral` のいずれかで完了している。
- When: ゲートがポーリングする。
- Then: そのポーリングで、判定 `success` でポーリングが終わる。

Scenario: チェックがまだ動いている場合、ゲートはポーリングを続ける

- Given: 先頭コミットの check run の1つが `in_progress` で、ほかは合格している。
- When: ゲートがポーリングする。
- Then: ゲートは判定を報告せず、ポーリング間隔だけ待って、もう一度ポーリングする。

Scenario: 失敗したチェックがあり、別のチェックがまだ動いている場合、ゲートはポーリングを続ける

- Given: check run の1つが `failure` で完了し、別の1つが `queued` である。
- When: ゲートがポーリングする。
- Then: ゲートは、queued の check run が完了するまで判定を報告せず、完了すると判定 `failure` で終わる。

Scenario: チェックが success、skipped、neutral 以外の conclusion で終わった場合、判定は failure になる

- Given: すべての check run が完了しており、1つの conclusion が `cancelled`、`timed_out`、`action_required`、`failure` のいずれかである。
- When: ゲートがポーリングする。
- Then: 判定 `failure` でポーリングが終わる。

Scenario: 先頭コミットに評価するチェックがない場合、判定は success になる

- Given: 先頭コミットに、ゲート自身のワークフローのもの以外の check run がなく、終わっていないワークフロー実行もない。
- When: ゲートがポーリングする。
- Then: 最初のポーリングで、判定 `success` でポーリングが終わる。

Scenario: ワークフロー実行が始まったがジョブがまだない場合、ゲートはそれを待つ

- Given: 先頭コミットのワークフロー実行が queued で、check run がまだなく、すでにある check run はすべて合格している。
- When: ゲートがポーリングする。
- Then: ゲートはそのワークフロー実行を未完了のチェック1件として数え、そのジョブが現れて終わるまでポーリングを続ける。

### ゲート自身を待たない

メンテナとして、ゲートには自分自身のワークフローを外してほしい。ゲートが自分自身を待たないようにするためである。

**受け入れ条件:**

Scenario: ゲートのジョブが動いている場合、そのジョブ自身の check run は評価されない

- Given: 先頭コミットで、ゲートのジョブの check run が `in_progress` で、ほかの check run はすべて合格している。
- When: ゲートがポーリングする。
- Then: 判定 `success` でポーリングが終わる。

Scenario: 同じコミットでゲートのワークフローの以前の実行がキャンセルされていた場合、それは評価されない

- Given: 先頭コミットに、ゲートのワークフローファイルの以前の実行による `cancelled` の check run があり、ほかの check run はすべて合格している。
- When: ゲートがポーリングする。
- Then: 判定 `success` でポーリングが終わる。

### ポーリングの上限をジョブのタイムアウトで決める

メンテナとして、ゲートが待つ時間の上限を1か所で決めたい。合わせ続ける必要のある2つのタイムアウトを持たないためである。

**受け入れ条件:**

Scenario: ジョブのタイムアウトまでにチェックが終わらない場合、ジョブは判定なしで終わる

- Given: ゲートのジョブに `timeout-minutes: 10` があり、check run の1つがそれより長く `in_progress` のままである。
- When: 10分が経つ。
- Then: GitHub がゲートのジョブを終わらせ、ゲートは判定を報告せず、出力も設定しない。

Scenario: ポーリング中にチェックの読み取りが失敗した場合、ゲートは次のポーリングで再試行する

- Given: ゲートがポーリングしており、GitHub が check run の要求の1つに、再試行のあともサーバーエラーを返す。
- When: そのポーリングが失敗する。
- Then: ジョブのログにエラーを含む警告が出て、ゲートはポーリング間隔のあとにもう一度ポーリングする。

Scenario: ポーリングを始める前に GitHub の rate limit に達していた場合、ジョブは rate limit のメッセージで失敗する

- Given: トークンには `actions: read` があり、GitHub は rate limit に達したことを理由に、先頭コミットのワークフロー実行の要求を拒否する。
- When: ゲートがポーリングを始めようとする。
- Then: ジョブは、GitHub API の rate limit に達したことを示し、`actions: read` には触れないメッセージとともに失敗し、ポーリングは行われない。

Scenario: `poll-interval-seconds` が正の整数でない場合、ジョブは失敗する

- Given: ワークフローが `poll-interval-seconds: '0'` を渡している。
- When: ゲートが起動する。
- Then: ジョブは、この入力は正の整数でなければならないというメッセージとともに失敗し、ポーリングは行われない。

## 機能要件

### 評価するチェック

**概要:** ゲートはポーリングのたびに、先頭コミットについて評価するチェックの一覧を作る。

**入力:** プルリクエストの先頭コミット、`ignore-checks` 入力、ゲート自身のワークフローファイル。

**出力:** そのポーリングで評価するチェック。

#### 適用する条件

##### 元になるもの

一覧は、GitHub Actions のものも GitHub App のものも区別せず、先頭コミットのすべての check run から始まる。
check run が再実行されていたときは、最新の試行だけを使う。
先頭コミットのワークフロー実行のうち、終わっておらず、check run がまだないものは、それぞれワークフローの名前の未完了のチェック1件を加える。

##### 除外

次のものを、この順に取り除く。

1. 置き換えられた実行の結果のうち、「より新しい実行に置き換えられたキャンセル済みの実行」の機能が無視するもの。
2. `ignore-checks` のルールに一致するチェック。
3. GitHub Actions の check run のうち、ゲート自身のワークフローファイルに属するもの。現在の実行のものも、同じコミットの以前の実行のものも含む。ゲート自身のワークフローファイルの、ジョブがまだないワークフロー実行も、未完了のチェックとして加えない。

##### 評価しないもの

以前からある commit status は読まない。commit status だけで報告する CI は、別の必須チェックとして登録する必要がある。

### 1つのチェックの読み方

**概要:** 評価する各チェックを、合格、不合格、未完了のどれかとして読む。

**入力:** check run の status と conclusion。

**出力:**

| status と conclusion | 読み方 |
| --- | --- |
| status が `completed` でない | 未完了 |
| `completed` で conclusion がない | 未完了 |
| `completed` で `success`、`skipped`、`neutral` のいずれか | 合格 |
| `completed` でそれ以外の conclusion。ゲートが知らない値も含む | 不合格 |

### 集約した判定

**概要:** 読み方を、ポーリングごとに1つの状態にまとめる。

**入力:** 評価するチェックの読み方。

**出力:** 未完了のチェックが1つでもあれば `pending`。そうでなく、不合格のチェックが1つでもあれば `failure`。それ以外は `success`。一覧が空なら `success`。

### ポーリング

**概要:** ゲートは、状態が `success` か `failure` になるまで評価を繰り返す。

**入力:** `poll-interval-seconds`（既定は `30`）: 正の整数。

**出力:** 集約した判定と、ポーリングの回数。

#### 適用する条件

##### 間隔

最初のポーリングはすぐに行う。`pending` だったポーリングと失敗したポーリングのあとは、次のポーリングまで間隔だけ待つ。

##### 終了

ポーリングは `success` か `failure` でだけ終わる。アクションにタイムアウトの入力はない。上限はジョブの `timeout-minutes` だけである。

#### 例外ケースでの振る舞い

##### ポーリングが失敗する

ポーリング中に GitHub からの読み取りが失敗したとき、ゲートは警告をログに出し、次のポーリングでもう一度試す。回数の上限はない。

##### ワークフロー実行を一覧できない

最初のポーリングの前に、ゲートは先頭コミットのワークフロー実行を一覧できることを確かめる。
GitHub が rate limit を理由にその要求を拒否したとき、ジョブは rate limit に達したことを示すメッセージとともに失敗し、ポーリングは始まらない。
GitHub がそれ以外の理由で拒否したとき、ジョブは `actions: read` の権限の名前を含むメッセージとともに失敗し、ポーリングは始まらない。

##### ポーリング中に rate limit に達する

rate limit を理由に拒否されたポーリングは、失敗したポーリングである。警告に rate limit のメッセージが入り、ゲートは次のポーリングでもう一度試す。

### アクションの出力

**概要:** ポーリングのあと、アクションは結果を表す出力を設定する。

**出力:**

| 出力 | 意味 |
| --- | --- |
| `state` | 集約した判定。`success` または `failure`。private mode がスキップしたときは `skipped` |
| `total-checks` | 最後のポーリングで読んだ check run の数。除外の前 |
| `evaluated-checks` | 最後のポーリングで評価したチェックの数 |
| `completed-checks` | 最後のポーリングで、評価したチェックのうち完了していた数 |
| `polled-iterations` | ポーリングの回数 |

private mode がスキップしたときは、[ゲートモード](../gate-modes/requirements.ja.md)に書いたとおり、`state` は `skipped`、ほかの出力は `0` になる。判定の前にジョブが失敗したとき、またはタイムアウトで終わったときは、出力を設定しない。

## データ要件

### 必要なデータ

- **check run:** 先頭コミットの各 check run の、名前、status、conclusion、リンク、元の GitHub App、check suite。ポーリングのたびに読み、保存しない。
- **ワークフロー実行:** 先頭コミットの各ワークフロー実行の、ワークフロー名、ワークフローファイル、イベント、status、check suite、リンク。ポーリングのたびに読み、保存しない。

### データ間の関係

GitHub Actions の check run は1つのワークフロー実行に属し、ワークフロー実行はそれぞれ自分の check suite を持つ。

### 個人情報

なし。

## 依存する外部サービス

- **GitHub**
  - **関連するユーザーストーリー:** すべて。
  - **依存する理由:** check run とワークフロー実行は GitHub のものである。
  - **契約・利用上の判断:** ポーリングのたびに、ワークフローのトークンで API を呼び、そのトークンの rate limit に数えられる。ゲートのジョブは、ポーリングしている間 runner を占有する。

## セキュリティ上の留意事項

トークンには `checks: read` と `actions: read` が必要である。集約は何も書き込まない。

## 未決事項

- **未確認: ポーリング中に rate limit に達したときにジョブを終えるか。** ポーリングの前の rate limit はジョブを失敗させる。ポーリング中の rate limit は次のポーリングで再試行する。ポーリング中も rate limit のエラーで終えるべきかは決まっていない。azu が決める。
