# automerge-gate

[English](product.md)

## 概要

automerge-gate は、プルリクエストに付くすべてのチェックを1つの必須チェックにまとめる GitHub Action です。
リポジトリは ruleset またはブランチ保護に、その1つのチェックだけを登録します。
このアクションは、プルリクエストの先頭コミットに付くほかのチェックを、ワークフローファイルや GitHub App の違いを問わずに待ち、1つにまとめた判定を報告します。
必須チェックが緑になると、GitHub 純正の auto-merge がプルリクエストをマージします。automerge-gate 自身はマージしません。

## 背景と解決する課題

### 背景

GitHub の ruleset とブランチ保護は、必須のステータスチェックを1つずつ名前で登録させ、登録したチェックを AND だけで組み合わせます。
auto-merge は、その一覧にあるチェックだけを待ちます（[Automatically merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request)）。

このプロジェクトの最初の版である check-suite-gate は、`check_suite.completed` に反応することで、ポーリングなしにチェックをまとめようとしました。
しかし GitHub Actions は、GitHub Actions 自身が作った check suite ではワークフローを起動しません。そのため、GitHub Actions だけを使うリポジトリではこの設計は一度も動きませんでした。
automerge-gate はこれを、その制限がないプルリクエストのイベントで起動するポーリング型のアクションに置き換えたものです。

### 解決する課題

必須チェックを名前で並べるメンテナは、実際に動くチェックと一覧を合わせ続ける必要があり、一覧は次の3つの形で壊れます。

- Renovate や Dependabot が、外部の GitHub App のチェックを持ち込んだり外したりする。
- monorepo は path filter を使うため、あるワークフローがプルリクエストによって動いたり現れなかったりする。
- ワークフローファイルを足すたびに ruleset を書き換える必要がある。

チェックを1つにまとめる既存の方法にも、それぞれ負担があります。
alls-green のように1つのワークフローの中でまとめるジョブは、ほかのワークフローファイルのジョブを見られません。
merge-gatekeeper のようにプルリクエストのイベントごとにポーリングするアクションは、マージするつもりがあるかどうかに関係なく、push のたびに runner を占有します。

## ターゲットエンドユーザー

### 内部リポジトリのメンテナ

- **特性:** fork からのプルリクエストを受けないリポジトリを保守している。ワークフローファイルが多く、Renovate や Dependabot のプルリクエストも多い monorepo であることが多い。runner の利用時間を費用として気にしている。
- **抱える課題:** 必須チェックの一覧が正しい状態を保てない。すべてのプルリクエストをポーリングすると、まだマージするつもりのないプルリクエストに runner の時間を使ってしまう。
- **利用文脈:** private mode を使う。auto-merge を有効にするか、プルリクエストを Approve し、すべてのチェックが通ったらマージされることを期待する。

### fork からのプルリクエストを受けるリポジトリのメンテナ

- **特性:** オープンソースのリポジトリを保守している。fork からのプルリクエストで起動したワークフローには、読み取り専用のトークンが渡される。
- **抱える課題:** 結果を API で書き込むゲートは、fork からのプルリクエストでは動かない。
- **利用文脈:** public mode を使う。ゲートのジョブ自身の結果が必須チェックになる。

## 提供価値

### 一覧の代わりに1つの必須チェック

- **対象:** 両方の種類のリポジトリのメンテナ。
- **内容:** ruleset には1つのチェックだけを書く。あとから足したワークフローや App のチェックも含めて、プルリクエストに付くすべてのチェックがそこにまとめられる。
- **提供理由:** 壊れるのは必須チェックの一覧である。1つにまとめたチェックなら、チェックが増減しても手入れが要らない。

### マージの意思に比例する runner の費用

- **対象:** 内部リポジトリのメンテナ。
- **内容:** private mode では、マージの意思があるプルリクエストだけをポーリングし、それ以外は数秒でスキップする。
- **提供理由:** ポーリングするゲートは、待っている間 runner を占有する。ポーリングをマージするつもりのあるプルリクエストに限れば、費用は push の数ではなくマージの数に比例する。

### 読み取り専用トークンで動くゲート

- **対象:** fork からのプルリクエストを受けるリポジトリのメンテナ。
- **内容:** public mode では、ゲートは読み取りの権限だけで動く。
- **提供理由:** GitHub は fork からのプルリクエストに読み取り専用のトークンを渡すため、判定は API への書き込みなしで伝える必要がある。

## 主要な概念

- **必須チェック:** ruleset またはブランチ保護に登録する1つのチェック名。既定の名前は `automerge-gate/all-passed`。
- **ゲートモード（gate mode）:** ゲートがいつ評価するかと、判定をどう報告するかの方式。`private` か `public` で、`gate-mode` 入力で選ぶ。
- **private mode:** fork からのプルリクエストがないリポジトリ向けのゲートモード。マージの意思があるときだけ評価し、判定を commit status として報告する。
- **public mode:** fork からのプルリクエストを受けるリポジトリ向けのゲートモード。起動したイベントごとに評価し、判定をゲートのジョブの結果として報告する。
- **マージの意思（merge intent）:** private mode で、誰かがそのプルリクエストをマージしたいことを示す合図。auto-merge が有効であるか、書き込み権限のあるレビュアーの有効な Approve レビューがあること。
- **context:** private mode が書き込む commit status の名前。必須チェックと同じにする。
- **check run:** GitHub の Checks API でコミットに報告される1つの結果。たとえば GitHub Actions のワークフローの1ジョブや、GitHub App の1つのチェック。
- **集約した判定:** 先頭コミットの check run からゲートが導く1つの結果。`success` か `failure`。
- **ポーリング:** 集約した判定が決まるまで、一定の間隔で check run を読み直すこと。
- **`ignore-checks` のルール:** 一致する check run を集約した判定から外すルール。
- **置き換えられた実行（replaced run）:** 先頭コミット上のワークフロー実行のうち、同じワークフローファイルかつ同じイベントの、より新しい実行があるもの。

## 成功の定義

リポジトリは必須チェックを1つ登録し、ワークフローや App が増減しても ruleset を編集しない。
マージの意思があるプルリクエストは、すべてのチェックが通れば追加の操作なしでマージされ、いずれかのチェックが失敗している間はブロックされたままになる。
private mode では、マージの意思がないプルリクエストは runner を占有しない。

## プロダクト開発を進める上での指針

- **マージは GitHub が行う。** アクションは判定を報告し、マージは GitHub 純正の auto-merge に任せる。マージの API は呼ばない。
- **判定の経路は1つ。** どちらのゲートモードでも、判定が必須チェックに届く経路は1つだけにする。競合する2つ目の合図を作らない。
- **タイムアウトは1つ。** ポーリングの上限はジョブの `timeout-minutes` だけにする。2つのタイムアウトは合わせ続ける必要があるため、アクションにタイムアウトの入力は置かない。
- **結果の読み方は GitHub に合わせる。** どの conclusion を合格とみなすかは、GitHub の必須ステータスチェックの決まり（[About status checks](https://docs.github.com/en/articles/about-status-checks)）に従う。独自の定義は作らない。
- **GitHub Actions の中で完結する。** 外部のサーバーも GitHub App も必要としない。
- **切り替えはワークフローファイルで行う。** どのイベントでゲートを起動するかで変わる振る舞いは、入力を増やさず、利用者のワークフローファイルで選ぶ。
- **リリースは書き換えられない。** リリースは書き換えられない semver タグで行い、動くメジャータグは置かない。固定したバージョンが書き換えられることがない。

## SLA・SLI・SLO

### SLA

なし。automerge-gate は、利用者自身のワークフローの中で、利用者の runner 上で動くアクションである。保証の対象となるホスト型のサービスがない。

### SLI・SLO

なし。このプロジェクトは、アクションを使うリポジトリから計測値を集めていない。
